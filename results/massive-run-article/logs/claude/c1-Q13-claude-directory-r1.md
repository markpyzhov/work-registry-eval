## Answer (as of the 2026-09-22 rule set)

### 1. Outputs — fail-closed, nothing is released
The governing rule is the Batch Failure Strategy decision recorded in WS-04: on **any unhandled failure the job aborts with no output file produced**, and temp files are **securely deleted** (`/Users/markpyzhov/VSCodeProjects/corpuses-arms/c1/work-states/WS-04-policy.md`, "Decisions and Superseded Directions" + `T015 / CIPH-25` evidence).

Mechanics from the originating decision thread (`/Users/markpyzhov/VSCodeProjects/corpuses-arms/c1/med-synth/communication/sources/slack/2026-06-12-batch-failures.md`):
- An unhandled worker exception aborts the **entire job**, not just the failing document — no partial exports even for files that already processed cleanly ("If we can't guarantee 100% of the batch is safe, we should fail-closed").
- The output buffer is purged; the core-engine exception hook (which also catches low-level segfaults) signals the controller to stop all active streams.
- An **atomic rename** is the last step, so the output folder stays empty until the final file is verified. Because the crash fired before any export was finalized, that rename never happens and the output directory remains empty.
- QA-validated: Diana's 2026-07-16 pass confirmed no output file on failure and secure temp deletion (`/Users/markpyzhov/VSCodeProjects/corpuses-arms/c1/med-synth/tasks/CIPH-25-Batch-Fail-Closed.md`). T015/CIPH-25 is **Completed**.

### 2. Temps — securely deleted via the OCR failure-path hooks
Since OCR ran, the ephemeral-cleanup path applies (`T025 / CIPH-35`, **Completed**):
- Cleanup is done by in-process `atexit`-style hooks covering **both the failure path and the completion path**; cron-based cleanup was explicitly superseded in favor of these for a "zero-residual footprint" (`/Users/markpyzhov/VSCodeProjects/corpuses-arms/c1/work-states/WS-07-storage.md`; `/Users/markpyzhov/VSCodeProjects/corpuses-arms/c1/med-synth/communication/sources/slack/2026-08-09-ocr-temp-cleanup-hooks.md`).
- Temps are purged from `/tmp/cipherdoc-*` immediately after processing; secure deletion was verified by Diana on 2026-08-11 on both failure and completion paths (`/Users/markpyzhov/VSCodeProjects/corpuses-arms/c1/med-synth/tasks/CIPH-35-Ephemeral-File-Cleanup.md`; `/Users/markpyzhov/VSCodeProjects/corpuses-arms/c1/med-synth/documentation/sources/2026-08-20-Ephemeral-File-Cleanup-Audit-Report.md`).
- The three artifact categories in scope, per the path trace (`/Users/markpyzhov/VSCodeProjects/corpuses-arms/c1/med-synth/documentation/sources/2026-08-20-Ephemeral-File-Cleanup-Review.md`): (a) per-page rasterized images in a process-local temp dir, (b) the **per-page OCR output buffer, written before confidence-threshold filtering is applied**, and (c) a run-level manifest of which pages fell back to OCR vs native extraction. Note (b) is why the 82% page's raw OCR text is a temp that gets deleted rather than an output.
- Documented limit: a **hard kill cannot be hooked**; the hooks only cover what the OCR branch can reach on its own. An unhandled worker exception is the covered failure path, so cleanup does fire here.

### 3. Crash report
A crash report is written to a **separate `audit_log.json` before shutdown**, capturing the **stack trace and the filename that triggered the fault** (`/Users/markpyzhov/VSCodeProjects/corpuses-arms/c1/med-synth/communication/sources/slack/2026-06-12-batch-failures.md`, Bob 2026-06-12 13:16; carried into the WS-04 decision as "Crash diagnostics go to a separate `audit_log.json`"). This is deliberately kept out of the purged output path — diagnostics survive even though no redacted output does. It is distinct from the compliance audit trail of T016/CIPH-26 (SHA-256 input hash + redaction-map JSON), which is a separate, still-unfinished system.

### 4. How the 90% manual-review rule applies here — it does not gate this abort
- The rule: 90% confidence threshold adopted for v1.0.0; anything below 90% is flagged for manual review, and confidence explicitly includes **OCR quality**, not just regex match score. Sub-threshold documents land in a quarantine folder and **won't be exported until a human confirms the redaction**, with metadata (confidence score, page number, reason) and UI indicators for reviewers (`/Users/markpyzhov/VSCodeProjects/corpuses-arms/c1/work-states/WS-04-policy.md`; `/Users/markpyzhov/VSCodeProjects/corpuses-arms/c1/med-synth/communication/sources/slack/2026-06-28-manual-review-threshold.md`).
- 82% is below 90%, so absent the crash this page would have been quarantined for manual review rather than exported.
- But the manual-review rule is a **hold on the export path**, and fail-closed removes the export path entirely: the job aborts with no output file produced and temps securely deleted. There is no surviving deliverable for a reviewer to approve, so the 90% rule yields no quarantined output for this run — the correct outcome is re-run after the crash is fixed, not human review of a partial result.
- Additional reason it does not bind as an enforcement rule today: **T014/CIPH-24 is still Active**. The end-to-end quarantine pass on 2026-09-18 exercised detection → quarantine → metadata → UI → approval, but Diana states the 90% threshold tuning itself "is still in progress… another round of testing before I'd call it locked" (`/Users/markpyzhov/VSCodeProjects/corpuses-arms/c1/med-synth/tasks/CIPH-24-Manual-Review-Threshold.md`).
- Evidence limit worth flagging: no source in this package states whether quarantine-folder entries or quarantine metadata written before the crash are treated as "outputs" to be purged or as retained diagnostics like `audit_log.json`. The only artifact the rule set explicitly exempts from purge is the crash report.
