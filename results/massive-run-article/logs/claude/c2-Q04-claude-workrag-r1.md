### Decision
- The earlier unresolved three-way choice — `RemoveAll()` vs. reattach vs. leaving cleanup to users — is **superseded**. Automatic `MultipartForm.RemoveAll()` is adopted. (`SRC-PR-01`, `SRC-NOTE-04`, `CMT-2026-03-002`)
- Configurability is deliberately deferred: an explicit option would only be added if users request it (SIG position; akats7 agreed on 2025-11-10 to hold off).

### Provenance and chronology
- **`SRC-ISSUE-01` — issue `#5946`** ("Using otelgin.Middleware will cause temporary MultipartForm files not to be destroyed"): opened 2024-07-25 by `zacklpx`; labels `bug`, `area: instrumentation`, `instrumentation: otelgin`; state **open** as collected (updated 2025-07-03). Root cause: otelgin replaces the request via `c.Request = c.Request.WithContext(ctx)`, so the parsed `MultipartForm` lands on the new request while the HTTP server still holds the original — nothing calls `RemoveAll()` at request end. Timeline includes cross-references from `#4588` (2024-11-21) and PR `#6609` (2025-01-13), and a `marked_as_duplicate` by `dmathieu` on 2025-07-02.
- **`SRC-PR-01` — PR `#6609`** ("fix(otelgin): remove multipartform temporary file") by `Yiling-J`: created 2025-01-13, last updated 2025-11-13, **state open**, branch `fix/gin_multipartform` → `main`, **+95 / −0 across 3 files**, no labels or milestone, description "Fix #5946". CLA signed; Codecov reported 75% patch coverage (3 lines uncovered), base 731 commits behind head.
- **Design debate on the PR**: `dmathieu` first suggested `Request.Clone(ctx)`; `Yiling-J` explained a deep clone does not help because `MultipartForm` is lazily initialized and nil at middleware time. `akats7` floated parsing the form in the middleware; `Yiling-J` opposed that (`maxMemory` should be the user's call) and at one point favored the **reattach** approach after failing to get guidance from the Go team (related: golang/go `#58809`, `#71382`, `#74455`). `flc1125` raised the side effect that `RemoveAll` in the otel middleware can force upstream middlewares (`m1(m2(otel(m3(fn))))`) that call `ParseMultipartForm` to re-create the form, causing extra allocations.
- **`SRC-NOTE-04` — Go SIG meeting 2025-10-16** (posted 2025-11-03 by `pellared`; attendees Tyler Yahn, Damien Mathieu, Bryan Boreham, David Ashpole, Robert Pająk): three options were weighed — `RemoveAll()`, leave to the user, or a configurable option with a default. **Damien proposed starting with automatic deletion and no explicit option**, adding one only if a strong need emerges; Tyler agreed the instrumentation is responsible for cleanup. The issue was noted as historical and potentially affecting virtually all HTTP middleware, not just otelgin.
- **November 2025 activity on the PR**: 2025-11-10 `akats7` said "we're good to resolve the conflicts and close this out"; `Yiling-J` resolved conflicts and reported otelgin package tests passing; `flc1125` requested extra unit tests for the upstream-middleware scenario and suggested the CHANGELOG line. `Yiling-J` added a test with one upstream and one downstream middleware. `flc1125` then contested the resulting behavior and offered prototype PR `#8161` (2025-11-11); `akats7` replied he was not clear which result was wrong and doubted the prototype, since cloning does not fix the fact that `WithContext` with an unparsed form leaves the server unable to clean up. Last PR update recorded: 2025-11-13.
