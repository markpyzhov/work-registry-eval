## Discussions

### 1. PR Review Request (Profiling / Runtime Tracer)

- Request for reviews on Nico’s PR related to Go runtime profiling (`pprof`) integration.
- Current behavior: each span creates a runtime tracing **task**, which introduces noise in profiles.
- Proposal:
  - Provide more control over task/region creation.
  - Different modes:
    - **Default**: create a task only for the root span.
    - **Auto mode**: task for root span, regions for child spans.
    - **Manual mode**: explicit task/region instrumentation by the user.
  - Optional async-style hint to indicate spans that cross goroutines.
- Key considerations:
  - Tasks can span multiple goroutines; regions must stay within a single goroutine.
  - Changing public tracing APIs is sensitive and tightly coupled to the specification.
  - Risk of breaking changes for existing instrumentation (e.g., Kafka libraries).
- Recommendation:
  - Start with a smaller, incremental change (e.g., ability to disable runtime tracing integration).
  - Open an issue describing:
    - Problem statement
    - Alternatives
    - Pros/cons
    - Links to Go runtime and `pprof` semantics
  - Keep current large PR as draft / proof of concept.

### 4. Kafka & Auto-Instrumentation Placement

- Question: Why some auto-instrumentations (e.g., Kafka) live in `opentelemetry-go` instead of `contrib`?
- Context:
  - Some instrumentations were historical donations.
  - Sarama instrumentation was deprecated and moved under Shopify due to lack of maintainers.
  - Auto-instrumentation landscape in Go is fragmented:
    - eBPF-based approaches
    - Compile-time instrumentation
    - Separate Auto-Instrumentation SIG
- Recommendation:
  - Join the Go Auto-Instrumentation SIG meeting.
  - Use the dedicated Slack channel for deeper discussion.
